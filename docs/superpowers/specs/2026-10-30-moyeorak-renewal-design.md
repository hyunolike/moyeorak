# 모여락 리뉴얼 설계

작성일: 2026-10-30
상태: 초안 (호스트 검토 대기)

## 1. 왜 바꾸는가

모여락은 유입은 충분한데 약속이 끝까지 정해지지 않는다. 운영하면서 반복해서 본 장면은 두 가지다.

- 링크를 받은 사람이 들어와서 투표를 안 하고 잠수를 탄다. 호스트가 단톡방에서 두세 번 재촉해야 겨우 채워지고, 마지막 한 명이 안 하면 결과가 안 나온다.
- 중간지점 결과를 보고도 "그래서 어디로 할까"는 다시 단톡방에서 정한다. 역 3개와 카페 목록은 정보이지 결정이 아니라서, 누군가 "그냥 강남으로 하자"라고 말해야 끝난다.

지금 모여락은 **표를 모으는 도구**다. 그런데 병목은 표를 모으는 과정이 아니라 그 앞(참여 부담)과 뒤(결정 부담)에 있다. 리뉴얼의 핵심은 모여락을 **약속을 끝까지 대신 정리해 주는 조율 비서**로 바꾸는 것이다. AI 에이전트는 이 비서의 두뇌이고, 캐릭터는 그 얼굴이다. 디자인은 "투표하는 화면"에서 "비서와 약속을 정하는 화면"으로 따라 바뀐다.

## 2. 성공 기준

리뉴얼 전 지표를 먼저 재고, 리뉴얼 후 같은 지표를 본다.

| 지표 | 정의 | 왜 보는가 |
|---|---|---|
| 확정률 | 생성된 모임 중 일정 또는 장소가 확정 상태까지 간 비율 | 핵심 지표. "끝까지 정해지는가" |
| 참여 완료율 | 모임 인원 중 실제로 투표(또는 가능 시간 입력)를 마친 사람 비율 | 잠수 문제를 직접 잰다 |
| 생성에서 확정까지 걸린 시간 | 모임 생성 시각부터 확정 시각까지 | 체감 속도 |
| 재사용률 | 한 번 호스트였던 사람이 30일 안에 모임을 또 만드는 비율 | 서비스가 실제로 도움이 됐는지 |
| 공유 수 | 모임당 공유 버튼 사용 횟수 | 유입 경로 건강 상태 |
| 제안 수락률 | 에이전트가 낸 제안 중 호스트가 받아들인 비율 | AI 기능이 쓸모 있는지 |

확정률과 참여 완료율은 지금 DB에서 바로 뽑을 수 있다(`schedule_poll.status`, `location_poll.status`, `participant`와 `schedule_vote` 조인). 리뉴얼 첫 주에 기존 DB에 SQL을 직접 돌려 이 여섯 개의 현재 값을 기록하고 기준선으로 삼는다. 새 앱에서는 관리자 지표 페이지가 같은 수치를 계속 보여준다.

## 3. 목표와 비목표

**목표**
- 참여자가 30초 안에 가능 시간을 남길 수 있다.
- 호스트가 재촉 메시지를 직접 쓰지 않아도 된다.
- 결과 화면이 "정보 목록"이 아니라 "제안 한두 개와 확정 버튼"으로 끝난다.
- 캐릭터가 서비스 안에서 말하고 움직이는 존재가 된다.
- 로그인 없이 쓰는 구조는 유지한다.

**비목표**
- 범용 챗봇을 만들지 않는다. 에이전트는 이 모임의 약속을 정하는 일만 한다.
- 식당 예약, 결제, 캘린더 동기화 같은 외부 시스템 쓰기 작업은 이번 범위에 없다.
- 회원 가입이나 소셜 로그인은 넣지 않는다.

**이렇게 되면 실패다**
- AI가 끼어들어서 오히려 화면이 복잡해지고 투표가 더 느려진다.
- 에이전트가 틀린 시간을 입력했는데 참여자가 알아채지 못한다.
- 기존 사용자가 캐릭터를 못 알아본다.
- 모임 하나에 드는 AI 비용이 수십 원을 넘는다.

## 4. 리뉴얼 방향

### 4.1 브랜드와 캐릭터: 합류점, "마주"

지금 캐릭터는 파란 구름 모양의 몸에 팔다리가 달린 마스코트인데 이름이 없고, 화면에서 장식 역할만 한다. 리뉴얼에서는 브랜드를 처음부터 새로 만들고, 새 캐릭터가 에이전트의 얼굴이 된다. 기존 로고, 캐릭터, 색은 이어 쓰지 않는다(호스트 결정, 2026-10-30). 확정된 에셋과 가이드는 `design/brand-v3/`에 있고, 기준 문서는 `design/brand-v3/BRAND.md`다.

- **콘셉트 "합류점":** 각자의 출발점에서 온 노선이 하나로 합쳐지는 구간을 역명판 모양 얼굴로 만들었다. 얼굴의 밝은 캡슐은 함께 가능한 시간과 중간지점, 두 눈은 그곳에 도착한 사람이다. 팔다리를 빼면 앱 아이콘이 되고 16px 파비콘까지 같은 얼굴을 쓴다.
- **이름:** 마주. 친구들이 마주 앉는 순간에서 따왔다. 서비스명과 달라서 화면에서 말하는 주체가 바로 구분된다.
- **성격:** 모임의 작은 역장. 재촉하는 총무보다 옆에서 정리해 주는 친구에 가깝다. 짧은 해요체로 확인한 사실을 먼저 말하고 다음 행동을 제안한다. 기다리는 사람에게 죄책감을 주지 않고, 사람이 확인하기 전에는 확정됐다고 말하지 않는다.
- **로고:** 직접 그린 한글 워드마크 "모여락"과 심벌. 가로형, 세로형, 흑백, 영문 워드마크를 쓴다.
- **두 계열:** 64px 이상 자리(랜딩, 빈 화면, 오류, OG, 앱 아이콘)는 무광 클레이 질감의 3D 렌더, 48px 이하(아바타, 칩, 파비콘)는 같은 비례의 2D 평면 얼굴을 쓴다. 3D 모델은 `design/brand-v3/tools/mazu.js`에서 파라미터로 표정을 만들고, `mazu.glb`로도 내보낸다.
- **표정 세트 8종:** 기본, 생각 중(제안 계산할 때), 기다림(응답 안 한 사람이 있을 때), 기쁨(좋은 소식), 미안함(외부 API 실패 등 오류), 안내(처음 온 사람에게 설명할 때), 축하(확정 직후), 졸림(아직 아무도 응답하지 않음). 각 표정은 정지 SVG 한 장과 2초 안쪽의 짧은 루프 애니메이션(Lottie 또는 CSS) 한 벌로 만든다.
- **말풍선 컴포넌트:** 마주가 말하는 곳은 항상 같은 말풍선 모양을 쓴다. 사용자가 "이건 AI가 한 말"임을 한눈에 알게 하기 위해서다.

### 4.2 디자인 시스템

- 색: 세 색이 역할을 하나씩 맡는다. 지금은 파랑과 청록 둘 다 "버튼색"이라 제안과 일반 동작이 구분되지 않는데, 이걸 끊기 위해서다. 토큰은 `design/brand-v3/tokens.css`를 그대로 가져다 쓴다.
  - 홍시 #F45B3F: 캐릭터와 브랜드 표면. 버튼에는 쓰지 않는다.
  - 숲 #176B5B: 확정, 저장 같은 주요 동작 버튼. 다크 모드에서는 #7DD4B5.
  - 신호 #F3CF58: **마주의 말풍선과 제안 카드에만** 쓴다.
  - 잉크 #202923(글자), 바탕 #F6F7F2(라이트 배경), 밤 #17251F(다크 배경).
  - 글자와 배경 조합은 WCAG AA 대비를 넘겨야 하며, 확인 결과는 `design/brand-v3/qa/contrast.json`에 있다.
- 글꼴: Pretendard 유지.
- 모바일 우선 레이아웃 유지. 데스크톱은 가운데 모바일 폭으로 띄우는 지금 방식 그대로.
- 컴포넌트는 기존 `shared/components`를 확장한다. 새로 필요한 것은 말풍선, 제안 카드, 진행 단계 표시, 자연어 입력창, 참여자 상태 칩(응답함/안 함)이다.
- 새 컴포넌트는 Storybook 스토리를 먼저 만든다. 기존 앱의 스토리 구성을 참고한다.

### 4.3 정보 구조: 두 개의 흐름에서 하나의 모임으로

지금은 첫 화면에서 "일정 조율하기"와 "중간지점 찾기" 중 하나를 고르고, 둘은 사실상 별개의 흐름이다. 리뉴얼에서는 **모임 하나가 단계를 거친다**.

```
모임 만들기 → 시간 모으기 → 장소 모으기 → 확정 → 당일 안내
```

- 호스트는 만들 때 "시간만", "장소만", "둘 다" 중 고를 수 있다. 하나만 골라도 나중에 나머지를 켤 수 있다.
- 모든 참여자가 보는 **모임 홈** 화면이 생긴다. 상단에 진행 단계, 가운데에 마주의 현재 말("3명이 응답했어요. 서연님 기다리는 중"), 아래에 지금 해야 할 일 버튼 하나.
- 시간표 화면과 지도 화면은 모임 홈 아래 단계로 들어간다.

### 4.4 참여자 입장 경험

링크를 받은 사람의 진입 장벽을 낮추는 것이 참여 완료율의 전부다.

1. 초대 화면에서 이름 입력. 이건 유지.
2. 가능 시간을 두 가지 방법 중 편한 쪽으로 남긴다.
   - **말로 하기:** "담주 평일 저녁 되고 수요일은 빼줘"처럼 적으면 마주가 시간표에 칠해 준다. 칠한 결과를 바로 시간표로 보여주고, 손으로 고칠 수 있다. 확인 전에는 저장하지 않는다.
   - **직접 칠하기:** 지금 시간표 그대로.
3. 출발지는 지금처럼 검색해서 등록. 여기에 "지난 모임에서 쓴 출발지" 바로 선택을 추가한다(localStorage 기반, 로그인 없음).

말로 하기 입력은 시간표 위에 입력창 하나로 둔다. 별도 채팅 화면을 만들지 않는다.

### 4.5 호스트 경험

- 모임 홈에서 누가 응답했고 누가 안 했는지 칩으로 보인다.
- **재촉하기** 버튼을 누르면 마주가 재촉 메시지를 써 준다. 호스트는 복사해서 단톡방에 붙여 넣거나 카카오 공유로 보낸다. 서비스가 직접 메시지를 보내지는 않는다(연락처를 모르고, 알림톡은 비용과 심사가 든다).
- 응답이 절반을 넘으면 마주가 호스트에게 먼저 묻는다. "3명 응답했는데, 지금 결과로 제안 받아볼까요? 아니면 서연님 기다릴까요?"

### 4.6 결정 경험: 제안 카드

결과 화면의 주인공을 목록에서 제안으로 바꾼다.

- 마주가 **제안을 최대 2개** 낸다. 각 제안은 한 장의 카드다.
  - 예: "11월 1일 일요일 오후 2시, 홍대입구역. 4명 모두 가능하고 다들 30분 안에 도착해요."
  - 카드 아래에 "이유 보기"를 펼치면 누가 몇 분 걸리는지, 왜 이 시간인지 나온다.
- 버튼은 "이걸로 확정"과 "다른 제안 보기" 둘뿐이다. 다른 제안을 누르면 조건을 말로 바꿀 수 있다. "조용한 카페로", "주차 되는 데로", "토요일로".
- 확정하면 마주가 **요약 카드**를 만든다. 날짜, 장소, 각자 출발지 기준 경로 요약, 지도 링크. 이미지로 저장하거나 텍스트로 복사해서 단톡방에 올릴 수 있다. 이 카드가 단톡방으로 돌아가는 마지막 순간을 모여락이 차지하게 한다.
- 기존 최적일정 목록과 역 3개 목록은 "전체 보기"로 한 단계 아래에 남긴다.

### 4.7 당일 안내

확정된 날 아침에 마주가 모임 홈 상단에 "오늘 2시 홍대입구역이에요. 합정에서 출발하면 1시 40분에 나오면 돼요"를 띄운다. 푸시 알림은 PWA가 이미 들어가 있으니 웹 푸시로 시작하되, 동의한 사람에게만 보낸다. 푸시 서버 구축이 부담이면 1차에서는 화면 안내만 하고 푸시는 뒤로 미룬다.

### 4.8 기술 선택: 새 스택으로 다시 짓는다

호스트가 기존 스택에 묶이지 않아도 된다고 했고, 저장소의 루트 `frontend/`와 `backend/`는 애초에 새 구현을 위해 비워 둔 자리다. 기존 코드를 고쳐 가는 대신 **루트에 TypeScript 풀스택 앱 하나(`app/`)를 새로 만든다.** 기존 `reference/`는 참고용으로 남긴다.

왜 바꾸는가.
- 지금 서비스는 링크 공유가 유입의 전부인데, SPA라 모임별 링크 미리보기(카카오톡 썸네일에 "현호님의 모임, 11월 1일")를 만들 수 없다. 서버 렌더링이 필요하다.
- 10월 커밋을 보면 이미 Render 무료 티어와 Neon으로 옮기면서 Spring 서버의 절전을 막으려 외부 모니터까지 붙였다. 서버리스에 맞는 런타임이면 이 문제가 사라진다.
- 에이전트의 스트리밍 응답, 도구 호출 반복, JSON 스키마 출력은 TypeScript 쪽 라이브러리가 가장 짧은 코드로 된다. 프론트와 백엔드가 한 언어면 타입도 한 번만 정의한다.
- 1~2명이 만드는 사이드 프로젝트라 배포 단위가 하나여야 유지가 된다.

선택한 스택.

| 영역 | 선택 | 이유 |
|---|---|---|
| 앱 | Next.js (App Router, TypeScript) | 서버 렌더링으로 링크 미리보기, Route Handler로 API, 서버리스 배포 |
| 스타일 | Tailwind CSS 4, Pretendard | 기존 디자인 토큰을 그대로 옮긴다 |
| 데이터 | PostgreSQL + PostGIS (Neon), Drizzle ORM | 역 공간 데이터와 기존 데이터를 그대로 쓴다. Drizzle은 SQL이 보이고 마이그레이션이 가볍다 |
| AI | Vercel AI SDK + OpenAI 호환 프로바이더로 NVIDIA API 연결 | `streamText`, 도구 호출 반복, `generateObject`(JSON 스키마)를 바로 쓴다 |
| 상태와 데이터 요청 | TanStack Query | 기존과 같다. 폴링으로 투표 현황을 갱신한다 |
| PWA | Serwist | 홈 화면 추가와 웹 푸시 준비 |
| 지도 | Naver Maps(표시), Kakao Local(검색), Google Routes(이동시간), ODsay(대중교통) | 기존 외부 연동 유지 |
| 테스트 | Vitest, Playwright | 단위와 화면 흐름 |
| 배포 | Vercel + Neon | 무료 티어로 시작, 콜드 스타트 문제 없음 |
| 모니터링 | Vercel Analytics와 로그, 지표는 앱 안의 관리자 페이지 | Grafana 스택은 서버가 없으니 뺀다 |

데이터 이전: 기존 Neon(또는 EC2 Postgres)의 `station` 테이블은 그대로 가져오고, 모임 데이터는 리뉴얼 배포 시점에 새 스키마로 한 번 옮긴다. 기존 링크(`/meetings/{id}/...`)는 새 앱에서 같은 경로로 열리게 해서 이미 공유된 링크가 깨지지 않게 한다.

## 5. AI 에이전트 설계

### 5.1 원칙

- 에이전트는 **읽고 제안**한다. 저장은 사용자가 확인 버튼을 누를 때만 일어난다.
- 모든 AI 호출은 백엔드에서 한다. 키는 서버에만 있다.
- 에이전트에게 주는 데이터는 모임 하나 범위로 제한한다. 다른 모임 데이터는 보지 못한다.
- 출발지는 동 단위 주소와 좌표만 보낸다. 상세 주소는 보내지 않는다.
- 호출마다 모임 ID와 용도, 토큰 수, 결과(수락 여부)를 기록한다.

### 5.2 기능별 설계

| 기능 | 입력 | 출력 | 방식 |
|---|---|---|---|
| 가능 시간 말로 입력 | 사용자 문장, 투표판 날짜 범위와 시간 범위, 오늘 날짜 | 30분 단위 `votedDates` 배열과 한 줄 확인 문장 | 구조화 출력(JSON 스키마 고정). 도구 없음 |
| 제안 만들기 | 투표 결과, 참여자별 출발지, 중간지점 추천 결과, 호스트가 말로 준 조건 | 제안 1~2개(시간, 장소, 이유, 참여자별 이동시간) | 도구 사용. 기존 Google Routes, Kakao Local, 주변 장소 검색 클라이언트를 도구로 노출 |
| 재촉 메시지 | 모임 정보, 응답 안 한 사람 이름, 마감 상황 | 카카오톡에 붙일 짧은 메시지 2가지 톤 | 단일 호출 |
| 조건 바꿔 다시 제안 | 직전 제안, 새 조건 문장 | 새 제안 | 제안 만들기와 같은 경로, 대화 이력 유지 |
| 요약 카드 | 확정 결과, 참여자별 경로 | 카드 본문 텍스트 | 단일 호출 |

### 5.3 모델과 호출 방식

AI는 **NVIDIA API**(build.nvidia.com의 NIM 엔드포인트, `https://integrate.api.nvidia.com/v1`)를 쓴다. 호스트의 결정이다.

- NVIDIA API는 OpenAI 호환 형식(`/v1/chat/completions`)이라 전용 SDK가 필요 없다. Vercel AI SDK의 OpenAI 호환 프로바이더(`@ai-sdk/openai-compatible`)에 `baseURL`만 NVIDIA 주소로 넣는다. 호출은 모두 Next.js 서버(Route Handler와 Server Action)에서 하고, 키와 모델명은 환경 변수 `NVIDIA_API_KEY`, `NVIDIA_MODEL_PARSE`, `NVIDIA_MODEL_SUGGEST`로 받는다.
- 모델은 하나로 고정하지 않고 **평가 세트(5.5)로 2~3개를 비교해 고른다.** 후보는 도구 호출을 지원하는 Nemotron 계열과 Llama 3.x 70B급 instruct 모델이다. 한국어 문장 이해가 핵심이라 한국어 평가 점수를 가장 먼저 본다. 정확한 모델 ID는 build.nvidia.com 카탈로그에서 확인해 설정값으로 넣는다.
- 용도별로 모델을 다르게 둘 수 있게 설정을 나눈다. 시간 파싱처럼 가벼운 일과 제안 만들기처럼 무거운 일을 같은 모델로 시작하되, 비용이나 속도 문제가 보이면 파싱만 작은 모델로 바꾼다.
- 시간 파싱은 JSON 스키마 응답(`response_format`의 JSON 스키마, 모델이 지원하지 않으면 NVIDIA의 `guided_json` 확장)으로 받고 **서버에서 반드시 다시 검증한다.** 투표판 범위를 벗어난 시간은 버리고 사용자에게 알린다. 모델이 스키마를 어기면 한 번 재시도하고, 그래도 안 되면 시간표 직접 입력으로 안내한다.
- 제안 만들기는 AI SDK의 도구 호출(`tools`)로 5.4의 도구를 노출하고, 반복 횟수는 8회로 제한한다.
- 응답은 `streamText`로 받아 그대로 클라이언트에 흘려보낸다. 마주가 "생각 중" 표정에서 말풍선이 차오르게 한다.
- 시스템 프롬프트(마주 말투, 규칙, 도구 설명)는 고정 문자열로 두고 모임 데이터는 그 뒤에 붙인다. NVIDIA API에는 프롬프트 캐싱 과금 혜택이 없으니 시스템 프롬프트 자체를 짧게 유지한다.
- 비용과 호출 제한: 모임 하나당 AI 호출 횟수에 상한을 두고(초기값 40회), 넘으면 마주가 "오늘은 여기까지만 도와줄 수 있어요"라고 말하고 수동 기능은 그대로 쓰게 한다. NVIDIA API의 분당 호출 제한과 요금은 계정 등급에 따라 다르므로 0단계에서 실제 계정으로 확인하고 상한값을 조정한다.
- 나중에 비용이나 지연 문제가 커지면 같은 모델을 NIM 컨테이너로 자체 호스팅하는 길이 열려 있다. API 형식이 같아서 코드 변경 없이 `base-url`만 바꾸면 된다.

### 5.4 도구 목록 (제안 에이전트용)

기존 서비스 메서드를 그대로 감싼다. 새 외부 연동은 없다.

- `get_vote_summary(meetingId)`: 시간대별 가능 인원과 이름
- `get_departures(meetingId)`: 참여자별 출발지(동 단위)와 좌표
- `recommend_midpoints(meetingId, departAt)`: 기존 중간지점 추천
- `travel_times(stationId, departAt)`: 참여자별 이동시간
- `search_nearby(stationId, category, keyword)`: 역 주변 장소

도구 결과는 그대로 넘기지 말고 필요한 필드만 추려 토큰을 아낀다.

### 5.5 평가

리뉴얼 전에 평가 세트를 만든다.

- 시간 파싱: 실제 단톡방에서 쓸 법한 문장 50개와 정답 시간대. "담주", "이번 주말 빼고", "평일 7시 이후" 같은 상대 표현을 꼭 넣는다. 정확도 95% 미만이면 출시하지 않는다.
- 제안: 과거 모임 데이터 20건으로 제안을 만들고, 호스트 본인이 "이거면 받아들였을까"를 채점한다.
- 모델 선정: 위 두 세트를 NVIDIA 카탈로그의 후보 모델 2~3개에 같이 돌려 정확도, 한국어 문장의 자연스러움, 응답 시간, 도구 호출 성공률을 표로 비교한다. 이 표를 보고 호스트가 모델을 고른다.

## 6. 데이터 설계

새 스키마는 Drizzle로 정의하고 마이그레이션 파일을 저장소에 둔다. 기존 테이블 이름과 구조는 참고만 하고 그대로 따르지 않는다.

- `meeting`: `id`(NanoId 21자, 기존 링크 호환), `host_name`, `participant_count`, `scope`(`schedule`, `location`, `both`), `status`(`scheduling`, `locating`, `confirmed`), `confirmed_at`, `created_at`.
- `participant`: `id`, `meeting_id`, `name`, `device_key`(기존 localStorageKey 역할), `is_host`.
- `schedule_poll`: `meeting_id`, `date_options`(date 배열), `start_minute`, `end_minute`, `confirmed_start`, `confirmed_end`.
- `schedule_vote`: `participant_id`, `slots`(timestamp 배열, 30분 단위).
- `location_vote`: `participant_id`, `label`(동 단위), `lat`, `lng`.
- `confirmed_location`: `meeting_id`, `station_id`, `name`, `lat`, `lng`.
- `station`: 기존 테이블을 그대로 가져온다. `geom`(PostGIS Point, 4326).
- `agent_suggestion`: `meeting_id`, `kind`, `payload`(jsonb), `status`(`proposed`, `accepted`, `rejected`), `created_at`, `resolved_at`. 제안 수락률은 여기서 나온다.
- `agent_call_log`: `meeting_id`, `purpose`, `model`, `input_tokens`, `output_tokens`, `latency_ms`, `ok`, `created_at`. 비용 상한과 모니터링에 쓴다.
- `meeting_event`: `meeting_id`, `type`(`created`, `joined`, `vote_done`, `shared`, `suggestion_viewed`, `confirmed` 등), `created_at`. 2장의 지표는 이 테이블로 계산한다.

API는 Next.js Route Handler로 `/api/*` 아래에 둔다. 기존 프론트가 쓰던 경로를 흉내 내지 않는다. 새 앱이 화면까지 함께 가지므로 호환할 클라이언트가 없다.

## 7. 단계별 진행

**0단계, 1~2주: 재기와 기반** — 기존 DB에 SQL을 직접 돌려 지표 여섯 개의 현재 값을 기록한다(코드 변경 없음). 평가 세트용 문장 50개를 모은다. 새 앱의 뼈대를 세운다: 프로젝트 생성, 스키마와 마이그레이션, 역 데이터 이전, 모임 생성과 참여와 투표의 최소 흐름, 관리자 지표 페이지, 배포. 이 단계가 끝나면 새 앱이 기존 앱과 같은 일을 할 수 있어야 한다(AI와 새 디자인은 아직 없음).

**1단계, 3~4주: 얼굴과 입구** — 마주 표정 세트와 말풍선, 디자인 토큰 정리, 모임 홈 화면, 가능 시간 말로 입력, 모임별 링크 미리보기. 여기서 기존 앱을 새 앱으로 교체 배포한다. 참여 완료율에 변화가 보여야 한다.

**2단계, 3~4주: 결정** — 제안 에이전트, 제안 카드, 확정 흐름, 재촉 메시지, 요약 카드. 확정률과 제안 수락률을 본다.

**3단계, 2주: 뒤처리** — 조건 바꿔 다시 제안, 지난 출발지 재사용, 당일 안내(화면), 웹 푸시(여력이 되면).

각 단계 끝에 0단계 지표와 비교한다. 1단계 뒤에 참여 완료율이 안 오르면 2단계로 가기 전에 입력 경험을 다시 본다.

## 8. 위험과 대응

| 위험 | 대응 |
|---|---|
| 시간 파싱이 틀린다 | 항상 시간표에 칠한 결과를 보여주고 확인 뒤에만 저장. 평가 세트 95% 기준 |
| AI 비용이 샌다 | 모임당 호출 상한, 짧은 시스템 프롬프트, 도구 결과 축약, 호출 로그 대시보드 |
| 한국어 상대 시간 표현을 모델이 잘못 읽는다 | 평가 세트에 상대 표현을 집중 배치, 오늘 날짜와 요일을 프롬프트에 명시, 결과를 시간표로 보여주고 확인 뒤 저장 |
| 외부 API(ODsay, Google) 실패로 제안을 못 만든다 | 마주가 미안함 표정으로 상황을 말하고 기존 목록 화면으로 안내. 시간만 있는 모임은 장소 없이도 제안 |
| 기존 사용자가 바뀐 화면에서 길을 잃는다 | 캐릭터 실루엣과 색 유지, 기존 시간표와 목록은 한 단계 아래에 그대로 둠 |
| 출발지 같은 개인정보가 AI로 나간다 | 동 단위와 좌표만 전송, 이름은 모임 안에서만 의미 있는 닉네임 |
| 제안이 재미없다(늘 같은 역) | 제안 2개는 서로 다른 축(시간 우선, 거리 우선)으로 만들게 프롬프트에 명시 |

## 9. 만드는 사람에게 맡기는 것

- 마주 표정 애니메이션의 실제 제작. 3D 렌더 8종과 2D 표정 8종, "생각 중" 루프 초안은 `design/brand-v3/character/`에 있고, 나머지 루프는 이 초안의 문법을 따라 만든다.
- 프롬프트 문구. 이 문서는 역할과 규칙만 정하고, 문장은 평가 세트로 다듬는다.
- 웹 푸시 서버 구성 여부와 시점.
- 제안 카드의 세부 레이아웃. 말풍선과 강조색 규칙만 지키면 된다.
- 요약 카드의 이미지 저장 구현 방식(서버 렌더링 또는 클라이언트 캔버스).

## 10. 이 문서에서 제가 정한 것

호스트가 직접 말하지 않았지만 제가 정한 선택이다. 바꾸고 싶으면 이 항목부터 보면 된다.

- 캐릭터 이름 "마주"와 성격 설정, 합류점 콘셉트와 색 역할 배분(새 브랜드로 가는 것 자체는 호스트의 결정)
- 기존 코드를 고치지 않고 Next.js 풀스택으로 새로 짓는 것과 그 스택 구성(4.8). 호스트는 "기존 스택을 안 써도 된다"고만 했고 무엇으로 할지는 제가 골랐다
- AI 호출을 Vercel AI SDK로 하는 것 (NVIDIA API를 쓰는 것 자체는 호스트의 결정)
- 모델을 하나로 못 박지 않고 평가 뒤에 고르는 것
- 재촉을 서비스가 직접 보내지 않고 호스트가 복사해 보내는 방식
- 제안을 최대 2개로 제한하는 것
- 두 흐름을 하나의 모임 단계로 합치는 정보 구조
- 모임당 AI 호출 상한 40회
- 단계 순서와 기간
